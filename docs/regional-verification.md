# Regional readiness and verification

A future regional deployment can use an SQS Standard test queue, the deployed engagement manager and the regional engagement source to verify readiness. The integration scenarios below specify evidence to collect in that environment. [Regional design](system-architecture.md)

The worker's PostgreSQL integration tests use separate JVMs and a controlled HTTP manager to check recovery after a process dies, a single effect per operation, the shared capacity limit, and progress for a small firm under contention. One local scenario covers a ready backlog. A second checks that a small-firm job can use spare capacity while slow status lookups keep the original large-firm attempts pending. The planning suite resumes in another JVM against a pinned fixture snapshot and checks the expired-snapshot outcome. The `demo` profile exercises two logical workers inside one JVM. [Two-JVM worker tests](../src/test/java/io/github/luisfm44/caseware/worker/bootstrap/DurableWorkerProcessIT.java) · [Planning snapshot tests](../src/test/java/io/github/luisfm44/caseware/worker/planning/PublicationSnapshotIT.java) · [Worker CI and demo evidence](evidence/README.md)

The version-selection and summary-validation references run independently and together over loopback HTTP. A test driver forwards the exact offered pair and checks the original receipt. These local runs use synthetic dependencies. The regional criteria cover live service contracts, durable recovery and delivery through AWS. ## Regional integration run

Use synthetic engagements in a regional test environment with at least two worker JVMs, a shared PostgreSQL execution ledger, a test queue and its dead-letter queue (DLQ). Record the deployed revisions, queue visibility and redrive settings, manager pool limit, workload and fault timing. If the queue uses fair delivery, record how producers map each firm to `MessageGroupId`. Keep the configured limit small enough to saturate on demand. Correlate observations using the same logical operation ID and distinct attempt IDs. Retain redacted ledger transitions, manager effect counts and reservation events, and timestamps for receive, downstream start, terminal commit and deletion. [Amazon SQS fair queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-fair-queues.html)

| Scenario | Pass condition | Evidence owner |
| --- | --- | --- |
| Duplicate delivery | Publish the same operation twice and overlap receives on different replicas. A fenced claim permits one execution path. The manager records one effect and the ledger records one terminal result. Repeated deliveries of a terminal operation are deleted without submitting again. | Worker and engagement manager |
| Visibility expires with work in flight | Let visibility expire while the first replica is active, then receive the message on another replica. The second replica cannot act on a live ledger claim. After claim expiry it reconciles the recorded attempt before any new submission. The first replica's stale claim cannot overwrite the new claim's result. | Worker |
| Crash after terminal commit | Stop a replica after its terminal result commits and before it calls `DeleteMessage`. Redelivery is acknowledged from the existing terminal result with no further submission and one recorded effect. | Worker |
| Delayed or unavailable status | Lose the submission response and interrupt status lookups while the manager may still be executing. The worker retains an unresolved attempt, retries the lookup with backoff and extends visibility while it owns the delivery. When status returns, the worker persists the authoritative outcome before deleting the message. | Worker and engagement manager |
| Late original request | Hold an authorized request until the worker loses its claim. A missing manager record leaves the outcome pending while the request can still arrive. If the manager subsequently confirms no effect, deliver the original request after the fence and verify rejection. A permitted replacement attempt produces at most one effect for the operation ID. | Engagement manager and worker |
| Terminal failure and duplicate delivery | Record a permanent rejection and, separately, exhaust the durable submission budget with confirmed no-effect outcomes. Commit each terminal result before deleting its delivery. Redeliver the same operations and verify the worker acknowledges each one from the ledger without a new authorization or a DLQ transfer. | Worker and engagement manager |
| DLQ and redrive | Exhaust the receive limit on an unacknowledged delivery and confirm the alarm. An uncertain attempt stays in the ledger and the reconciler queries the manager independently of SQS. After diagnosing the failure, redrive the message and verify its operation ID, attempt history and budget still match. Redriving a terminal operation preserves its result and effect count. For an unresolved operation, a new attempt needs a confirmed no-effect outcome, an enforced late-request fence and an available authorization. | Regional operations, worker and engagement manager |
| Global capacity | Drive a backlog through at least two JVMs and include any other callers that share their manager pool. Stop a replica while its manager operation is active. The manager's event trace shows that concurrent active operations stay within the configured pool limit throughout recovery. Once the manager confirms completion or enforced cancellation, a waiting operation can use the released capacity. | Engagement manager and regional operations |
| Capacity denial and budget | Submit while the manager pool is full. Its authoritative denial fences that attempt and leaves the job ready after deferral, with the durable submission budget restored. Repeat with a lost denial response. The worker restores the budget only after authoritative reconciliation of the denial. When a slot opens, a fresh attempt can start. | Worker and engagement manager |
| Quiet-firm wait | Compare the same quiet-firm arrival pattern with and without a large firm's sustained backlog. Under contention, measure elapsed time from enqueue to downstream start for the quiet firm. Agree the latency target and acceptable degradation before the run, then record the baseline, observed percentiles and target. Also verify the manager limit throughout. | Regional operations and worker |
| Quiet firm during slow reconciliation | Keep the manager below its pool limit with large-firm attempts whose lookups remain pending. Enqueue a quiet-firm job and verify that it starts within the agreed target and completes once while the original large-firm reservations remain active. Check the peak against the manager limit and confirm that the reconciler continues to make lookup progress. | Regional operations, worker and engagement manager |
| Outbox replay | Roll back a page and verify that it produces no message. Crash the relay after page commit and before send, then after SQS accepts a send and before the relay records success. Committed jobs reach SQS after restart. Duplicate messages retain the operation ID and yield one effect per operation. | Exception planner and outbox relay |
| Real source snapshot recovery | Commit a first page, insert and remove eligible engagements and change an engagement revision in the live source, then restart the planner in a fresh JVM. The real source accepts the stored snapshot ID and cursor, and the final set of operation IDs matches the original snapshot exactly. Repeat after expiry and verify that the planner reports the failure and leaves the checkpoint and committed jobs intact. Record the tested snapshot retention and the recovery interval it covers. | Engagement source and exception planner |

Exercise the DLQ with a message that has no downstream effect and with an unresolved operation. Record the DLQ entry and the unresolved ledger state separately. Base the redrive limit and retention periods on the recovery run and include time for operator diagnosis. A delivery's visibility window and the ledger claim can expire independently of the manager reservation. [SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html) · [SQS dead-letter queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html)

## Operational signals

| Signal | Source | Owner action |
| --- | --- | --- |
| Oldest ready work | Track `ApproximateAgeOfOldestMessage` and `ApproximateNumberOfMessagesVisible` on the source queue. With SQS fair queues, compare `ApproximateAgeOfOldestMessageInQuietGroups` under contention. Measure enqueue-to-start latency from correlated events. Where the producer uses an outbox, monitor the oldest unsent committed entry separately. | Regional operations investigates delivery delay and relay backlog. |
| Oldest unresolved operation | Measure elapsed time since the worker ledger recorded the current uncertain attempt. Track the oldest age and unresolved count by region and pool, including attempts whose delivery moved to the DLQ. | Worker on-call checks status availability and starts the reconciliation runbook when age exceeds the agreed threshold. |
| Occupied permits | The manager emits current occupied permits, configured limit and admission denials per pool. Use its operation lifecycle events to calculate the actual peak during readiness tests. | Manager on-call investigates sustained saturation and any limit breach. |
| Dead-letter backlog | Monitor `ApproximateNumberOfMessagesVisible` on the DLQ and correlate affected operation IDs with the ledger. | Regional operations diagnoses failures before redrive and escalates uncertain outcomes to the worker and manager owners. |

SQS metrics are approximate. Repeatedly received messages can be excluded from the oldest-message metric. Use the manager's events and gauges to measure active operations. Set alert thresholds with service owners from the observed recovery and load tests. [SQS CloudWatch metrics](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-available-cloudwatch-metrics.html)

## Readiness record

Attach the integration run and evidence to the regional deployment work item. Record the result for every applicable scenario, the queue and manager settings used, the approved fairness and recovery thresholds, and the owners for operational alerts. The worker, engagement manager, engagement source and regional operations owners review that evidence before accepting regional readiness.
